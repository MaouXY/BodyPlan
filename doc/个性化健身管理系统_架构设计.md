# 个性化健身管理系统架构设计

## 1. 总体架构

系统采用 Spring Boot + Vue + Android 的前后端分离架构。Android 端负责普通用户高频使用场景，Vue 端负责后台管理与内容运营，Spring Boot 后端负责统一接口、业务逻辑、推荐计划、数据统计和权限控制。后端版本与既有模板工程统一为 Spring Boot 3.5.8（JDK 17），直接复用统一返回结构、全局异常处理、JWT 鉴权、MyBatis-Plus 分页和接口文档基建。

功能按阶段交付：阶段 1 先打通“建档 → 推荐 → 打卡”闭环，阶段 2 补动作视频与复测调整，阶段 3~5 依次补跑步记录、分享与排行榜。阶段划分见《个性化健身管理系统_分阶段实现计划》。

| 层次 | 技术 | 作用 |
|---|---|---|
| 移动端 | Android | 身体数据录入、目标选择、计划查看、训练打卡、提醒、分享和排名 |
| 管理端 | Vue 3 | 用户管理、视频管理、标签管理、数据统计 |
| 接口层 | Spring Boot 3.5.8 REST API | 为 Android 和 Vue 提供统一业务接口 |
| 业务层 | 用户画像、评分、推荐、计划、打卡、排名服务 | 承载系统核心业务逻辑 |
| 数据层 | MySQL 8.x | 存储业务数据；排行榜与统计由聚合查询实现，不引入 Redis |

## 2. 架构设计目标

1. 支撑用户从身体数据录入到计划执行的完整闭环。
2. 支持基于身体数据、偏好、伤病和体能测试的个性化推荐。
3. 支持每日打卡、跑步记录、排名和分享等激励能力。
4. 支持周期复测后重新评分和动态调整计划。
5. 后续可扩展饮食管理、穿戴设备接入和 AI 私教等功能。

## 3. 系统模块划分

### 3.1 Android 用户端模块

阶段 1 只做 4 个界面，先把闭环跑通，其余页面在后续阶段补齐。

**阶段 1（闭环必需）**

- 登录注册页（登录、注册、退出）
- 建档问卷页（身体数据 + 目标 + 偏好 + 每周时间与提醒 + 伤病与限制 + 体能测试，分步填写）
- 我的计划页（当前计划、每周安排、动作清单、推荐依据）
- 今日打卡页（今日任务、逐项完成打卡、打卡日历与连续天数）

**阶段 2**

- 动作视频跟练页（筛选、播放、动作要点）
- 身体数据复测页（复测录入、趋势展示、计划调整提示）

**阶段 3~5**

- 跑步记录页（距离、用时、配速、历史）
- 分享页（跑步与打卡分享卡片）
- 排行榜页（日/周/月：跑步距离、完成次数、连续打卡）

### 3.2 Vue 管理端模块

- 用户管理（阶段 1）
- 身体数据查看（阶段 1）
- 动作标签管理（阶段 1）
- 打卡数据统计（阶段 1）
- 动作视频管理（阶段 2）
- 推荐记录查看（阶段 2）
- 排行榜统计（阶段 5）

说明：不做“训练计划模板管理”。训练计划由后端按规则从动作库中筛选生成，规则以代码常量维护，避免额外的模板配置与维护成本。

### 3.3 Spring Boot 后端模块

- 认证授权模块（阶段 1）
- 用户档案模块（身体数据、目标、偏好、伤病限制，阶段 1）
- 体能评估模块（阶段 1）
- 计划生成模块（含推荐记录，阶段 1）
- 打卡记录模块（阶段 1）
- 统计与排行模块（阶段 1 统计、阶段 5 排行）
- 动作视频模块（阶段 2）
- 复测调整模块（阶段 2）
- 跑步记录模块（阶段 3）
- 日志与异常处理模块（阶段 0 基座已具备）

说明：不再单独拆分“目标推荐”“用户画像”“提醒任务”模块。目标推荐与画像计算内聚在计划生成模块中；提醒只做设置项存储，不做推送任务。

## 4. 核心业务流程设计

### 4.1 用户建档流程

1. 用户注册并登录。
2. 用户录入性别、年龄、身高、体重和身体类型。
3. 系统计算 BMI 等基础指标。
4. 系统生成初始身体画像。

### 4.2 目标推荐流程

1. 系统读取用户基础身体数据。
2. 根据 BMI、年龄、性别和身体类型推荐目标。
3. 前端展示推荐目标及说明。
4. 用户确认阶段性目标。

### 4.3 计划生成流程

1. 用户选择重点增强部位和喜欢的运动类型。
2. 用户设置每周训练日期、每日运动时长和提醒时间。
3. 用户填写伤病情况、场地限制、噪音限制和是否可跳跃。
4. 用户提交俯卧撑、深蹲、卷腹、爬楼状态等体能测试信息。
5. 系统综合用户画像、目标、偏好、限制和体能等级，按 6.2 的规则从动作库中筛选动作并生成计划（不使用计划模板表）。
6. 系统生成包含每日任务、动作视频、组数、次数和休息安排的训练计划，并把推荐依据写入推荐记录。

### 4.4 每日打卡流程

1. 用户查看今日训练任务。
2. 用户根据动作视频完成训练。
3. 用户填写完成的组数、次数、时长或跑步距离。
4. 系统保存打卡记录并更新计划完成度。
5. 系统更新连续打卡天数、排行榜和训练统计。

### 4.5 复测调整流程

1. 用户阶段性重新录入体重、身体类型等数据。
2. 系统对比历史身体数据变化。
3. 系统更新身体评分和目标进度。
4. 若用户接近目标或训练能力提升，系统调整后续计划难度。
5. 新计划继续进入每日打卡流程。

## 5. 数据架构设计

共 11 张表，建表脚本见 `BodyPlanApi/sql/`。建档问卷中的目标、偏好、训练时间、伤病限制等都是“与用户一对一、一次性填写”的数据，合并进用户档案一张表；只有需要保留多次历史的数据才单独建表。

| 表名 | 说明 |
|---|---|
| `user_account` | 用户账号（登录名、密码散列、昵称、手机号、角色、状态） |
| `user_profile` | 用户档案（建档问卷合并表） |
| `body_data` | 身体数据记录（可多条，含 BMI 与身体评分） |
| `fitness_test` | 体能测试记录（可多条，产出 L1/L2/L3 等级） |
| `exercise` | 动作视频（部位、类型、难度、场景、器械、禁忌标签、视频地址、动作要点） |
| `exercise_tag` | 动作标签字典（筛选与表单选项） |
| `training_plan` | 训练计划（目标、难度、每周天数、起止日期、状态、推荐依据） |
| `training_plan_item` | 训练计划明细（第几天、动作、组数、次数、时长、休息、完成状态） |
| `checkin_record` | 每日打卡记录 |
| `running_record` | 跑步记录（阶段 3） |
| `recommend_log` | 推荐记录（输入快照、命中规则、被排除动作数、推荐原因） |

说明：取消 `fitness_goal`、`user_preference`、`training_schedule`、`injury_constraint`、`score_record`、`ranking_record` 六张表。前四张并入 `user_profile`；身体评分并入 `body_data.score`；排行榜不落表，由聚合查询实时计算。

### 5.2 数据关系

- 一个用户对应一条 `user_account` 与一条 `user_profile`。
- 一个用户可以有多条 `body_data` 与 `fitness_test` 记录，用于趋势分析和难度调整。
- 一个用户同时只有一条状态为 `ACTIVE` 的 `training_plan`，复测调整时旧计划置为 `REPLACED`。
- 一个训练计划由多条 `training_plan_item` 组成，每条明细指向一个动作，并保存动作名称快照，避免列表页联表。
- 一条 `checkin_record` 关联用户、训练计划和具体计划明细；`(user_id, plan_item_id, training_date)` 建唯一键，天然防止重复打卡。
- `recommend_log` 记录本次推荐使用的输入、命中的规则和被排除的动作数，用于解释“计划为什么这样推荐”。
- 跑步记录是打卡之外的独立记录；排行榜由打卡记录与跑步记录聚合计算，不单独落表。

## 6. 推荐与评分设计

推荐只需要 5 个字段参与匹配，其余字段仅存档展示、不进入算法，避免规则组合爆炸：

**参与匹配（5 项）**

1. 主目标（减脂瘦身 / 增肌塑形 / 提升心肺 / 改善体态 / 局部力量 / 日常体能）
2. 体能等级 L1 / L2 / L3（由体能测试结果换算）
3. 重点部位
4. 伤病禁忌（膝 / 腰 / 肩 / 腕 / 心肺）
5. 训练场景与限制（宿舍、小场地、零噪音、无跳跃、无器械）

**仅存档展示**

性别、年龄、身高、体重、身体类型、次目标、喜欢的运动类型、每周可训练时间、每日运动时长、是否开启提醒、历史打卡完成度。

### 6.2 计划匹配策略

系统采用“规则 + 排除式匹配”，三步即可生成一份可解释的计划：

1. **定难度**：由体能测试结果换算等级（L1/L2/L3），从动作库中取 `difficulty` 不高于该等级的动作。
2. **筛动作**：按主目标与重点部位筛出候选动作，再按动作的禁忌标签与用户的伤病、场景、器械限制做排除（例如用户有膝伤且不能跳跃，则排除带 `KNEE` 标签的动作；无器械则排除哑铃、弹力带动作）。被排除的动作数写入 `recommend_log.excluded_count`。
3. **铺每周**：按每周可训练天数把候选动作分配到各天（同一部位不连续两天），按每日运动时长决定动作个数（例如 30 分钟约 4 个动作），并为每个动作给出组数、次数或时长与组间休息。

生成结果写入 `training_plan` 与 `training_plan_item`，同时把输入快照、命中规则和推荐原因写入 `recommend_log`，前端展示“推荐依据”。用户复测后重新执行同一套规则，即可得到难度调整后的新计划——规则不变、结果可解释，便于答辩演示与调试。

## 7. 接口设计原则

- 接口按业务资源划分，如用户档案、身体数据、目标、计划、打卡、跑步、排名。
- 所有接口采用统一返回结构。
- 写操作必须进行参数校验。
- 列表接口支持分页、排序和条件筛选。
- 推荐、计划生成和复测调整接口需要记录推荐依据。
- 发生异常时，后端需要记录包含业务场景、用户标识和真实异常信息的运行日志。

## 8. 部署架构

### 8.1 开发部署

- Android 端连接测试环境 API。
- Vue 管理端本地运行并调用后端接口。
- Spring Boot 服务本地或测试服务器启动。
- MySQL 存储业务数据（排行榜与统计由聚合查询实现，不引入 Redis）。

### 8.2 生产部署

- Nginx 托管 Vue 静态资源并反向代理后端接口。
- Spring Boot 应用部署在 Linux 服务器。
- MySQL 独立部署并定期备份。
- 不部署 Redis；如后续数据量增长再考虑引入缓存。
- 视频资源可存储在对象存储或媒体服务器。

## 9. 技术选型理由

### 9.1 Spring Boot 3.5.8

- 适合快速开发 REST API。
- 生态成熟，便于集成 MyBatis-Plus、JWT、参数校验等组件。
- 与既有模板工程版本一致（Spring Boot 3.5.8 + JDK 17），可直接复用统一返回结构、全局异常处理、JWT 鉴权、MyBatis-Plus 分页与 Knife4j 接口文档基建，减少重复搭建成本。
- 适合承载计划推荐、打卡统计和排行榜等业务服务。

### 9.2 Vue

- 适合开发后台管理端。
- 组件化程度高，便于实现表格、表单、筛选和统计页面。

### 9.3 Android

- 适合承载用户每日训练、打卡、提醒、跑步记录和分享等高频移动场景。
- 可结合系统通知能力实现训练提醒。

## 10. 架构结论

本系统采用 Android 用户端、Vue 管理端和 Spring Boot 后端协同的三端架构。整体架构围绕“建档评估、计划推荐、训练执行、激励反馈、复测调整”展开，能够支撑类似 Keep 的个性化健身管理核心体验，并具备后续扩展饮食、社区、智能设备和 AI 推荐能力的空间。功能按“阶段 1 闭环 → 阶段 2 视频与复测 → 阶段 3~5 跑步、分享、排名”交付，阶段 1 结束即可演示与答辩。
